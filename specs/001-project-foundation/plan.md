# Implementation Plan: Project Foundation

**Branch**: `main` (spec directory `001-project-foundation`; no feature branch exists, as the git extension is not installed) | **Date**: 2026-09-05 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-project-foundation/spec.md`

## Summary

Establish the minimum foundation to build, run, configure, test, and develop the Order
Processing System, with no domain functionality. The spec's 35 functional requirements reduce
to six independently shippable slices: a runnable service with a health check, reproducible
migrations, a trustworthy serial test harness on a real database, fail-fast configuration, a
lint and type gate, and a placeholder scheduled task proving recurring work can run.

The approach is a single NestJS service in TypeScript on Node.js, persisting to one SQLite
file reached exclusively through Drizzle, with drizzle-kit producing committed migrations.
Every version below was resolved against the live registry rather than assumed.

This plan was regenerated after a second clarification round on 2026-09-05, which closed three
of the six items the first pass left open: the shutdown drain default, the scheduled task
interval default, and the derivation rule for the minimum Node version.

The remaining two were then settled by experiment on the same day: the SQLite driver is
`better-sqlite3@13.0.3` and the compiler is `typescript@5.9.3`. **No NEEDS CLARIFICATION
remains that blocks implementation.** Only runtime latency targets stay deferred, correctly,
because spec 001 has no domain endpoint to measure. See [research.md](./research.md).

## Technical Context

**Language/Version**: TypeScript on Node.js. Verified on this development host: Node
`v24.19.0`, npm `11.17.0`. `@nestjs/core@12.0.1` declares `engines.node >= 20`.

FR-003 fixes a derivation rule rather than a number: the documented floor is the highest
minimum required by any direct dependency, recomputed whenever dependencies change. With the
driver settled, two dependencies declare a floor, `@nestjs/core` at `>= 20` and
`better-sqlite3` at `>= 22`. The documented minimum is therefore **Node 22**, developed
against Node 24. It moved from 20 without anyone deciding it should, which is the rule doing
its job.

TypeScript is **`5.9.3`**, resolved by experiment. TypeScript 7.0.2 was tested and works:
NestJS dependency injection resolved correctly under it, so the decorator metadata concern was
unfounded. It was rejected on ergonomics. TS 7 removed `moduleResolution: node10`, which is
what NestJS tooling generates, so adopting it means diverging from every NestJS scaffold,
document, and Jest preset. On a project whose purpose is a low-friction foundation, that costs
more than the faster compiler returns. TS 7 with `nodenext/nodenext` compiles cleanly and
remains the configuration to use if the project later migrates.

**Primary Dependencies**: Resolved from the registry on 2026-09-05.

| Package | Version | Note |
|---------|---------|------|
| `@nestjs/core`, `@nestjs/common`, `@nestjs/platform-express` | `12.0.1` | `engines.node >= 20`, satisfied by 24.19.0 |
| `@nestjs/schedule` | `12.0.1` | peers `@nestjs/core` v11 or v12, satisfied |
| `drizzle-orm` | `0.45.2` | peers both candidate drivers |
| `drizzle-kit` | `0.31.10` | migration generation and application |
| `better-sqlite3` | `13.0.3` | Selected by experiment. Ships prebuilt binaries in the tarball; `engines.node >= 22` sets the Node floor |
| `typescript` | `5.9.3` | Selected by experiment. Clean compile with the NestJS-default `commonjs` + `node` config |
| `jest` | `30.5.1` | NestJS scaffolding default |

The configuration validation library is deliberately left unpinned. It is a routine choice for
the task phase, not a planning risk, and pinning a version I have not verified against NestJS
12 would be inventing precision.

**Storage**: A single SQLite database file. Schema defined in Drizzle schema modules as the
single source of truth (FR-010); migrations generated by drizzle-kit and committed (FR-012).
Connection pragmas applied at startup on every connection, test connections included
(FR-013): `journal_mode = WAL`, `foreign_keys = ON`, and a non-zero `busy_timeout`. No second
persistence path exists (FR-014).

**Testing**: Jest `30.5.1`, executing test files serially rather than in parallel (FR-016, as
clarified on 2026-09-05), against a real file-backed throwaway database created per run and
removed when the run ends (FR-018). Per-test cleanup uses `DELETE FROM` rather than
`TRUNCATE`, which SQLite does not have (Constitution VI). A run matching zero tests must exit
non-zero (FR-019).

**Target Platform**: Node.js service. No browser, mobile, or desktop surface. Development host
verified as Windows 11 on `win32-x64`. **Python is not on PATH**, so `node-gyp` cannot compile
a native addon from source on this machine.

That constraint was expected to decide the driver question and turned out not to bind at all:
`better-sqlite3@13.0.3` ships prebuilt binaries for eight platform targets inside the npm
tarball, including `win32-x64`, and installed in two seconds without invoking node-gyp. The
constraint still stands as a property of this host and remains the reason to check any future
native dependency before adopting it.

**Project Type**: Single backend web service. No frontend, no split between API and worker
processes, one deployable unit.

**Performance Goals**: Grounded in the spec's success criteria. All are developer-workflow
targets rather than runtime targets, which is the honest state of a foundation spec.

- Clone to healthy service in under 10 minutes (SC-001)
- Full quality and test verification within a two-minute budget (SC-003). Clarified as an
  **advisory target, not an enforced timing gate**, because a wall-clock gate fails for
  reasons unrelated to the code and erodes the credibility of the gates that matter, FR-019's
  zero-test check included.
- Misconfigured startup rejected within 5 seconds (SC-004)
- Scheduled task fires on every interval across **at least six consecutive intervals**, zero
  overlaps (SC-008)

Runtime request latency and throughput targets are **NEEDS CLARIFICATION**. Spec 001
introduces no domain endpoint to measure, and the clarification pass explicitly recorded this
category as Outstanding and low impact. A number invented here would become an untestable
acceptance criterion.

**Constraints**:

- Single process against a single database file, single writer (Constitution, Scope section).
- Shutdown drains in-flight work under a configurable timeout defaulting to **ten seconds**,
  then force-exits (FR-032, FR-033). Ten seconds is orders of magnitude longer than the
  longest unit of work 001 can produce, which is a health request plus an instantaneous
  heartbeat, while still surfacing a hang quickly. Container grace-period conventions were
  considered and rejected as importing a constraint from a deployment model this spec
  excludes.
- The placeholder scheduled task interval defaults to **five minutes** (FR-029), matching the
  cadence the constitution sets for the future order promotion job so the placeholder
  rehearses real timing. That default exceeds the entire SC-003 budget, so FR-029 requires
  tests to override the interval through configuration, and SC-008 was rewritten to express
  its observation window in intervals rather than wall-clock minutes.
- Migrations are **never applied during startup** (FR-015). The service refuses to start while
  any migration is pending, naming it. This closes a race that matters specifically on a
  single-writer engine, where two processes booting at once could otherwise both attempt to
  migrate.
- All log output is machine-parseable structured records on stdout, one format in every
  environment (FR-031, as clarified on 2026-09-05).

**Scale/Scope**: The scope of this feature is grounded and closed: 35 functional requirements,
6 prioritized user stories, 11 success criteria, 0 domain entities. Expected order volume,
database growth, and concurrent user counts are **NEEDS CLARIFICATION** and belong to a later
domain spec. No requirement in 001 depends on them.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

Evaluated against constitution v2.0.0. Most principles govern domain behaviour that spec 001
deliberately excludes, so the useful question for each is not "does 001 comply" but "does 001
leave it implementable".

### Initial gate, before Phase 0

| Principle | Status | Assessment |
|-----------|--------|------------|
| I. Centralized State Machine | **PASS, not exercised** | 001 introduces no order status and no transition logic. Nothing to violate and nothing to enable. |
| II. Lock-Free Atomic Transitions | **PASS, with a foundation obligation** | Not exercised, but the driver chosen here must surface a changed-row count, since that count is what a 409 is decided from. Both candidates do. Recorded as a hard filter in research. |
| III. Bounded Background Processing | **PASS, partially exercised** | FR-026 to FR-029 add the scheduler and require overlap prevention, which is the reusable half of this principle. The constitution's own rationale anticipates a synchronous driver and names the iteration cap as the mitigation, so a blocking driver is not itself a violation. |
| IV. Exact-Integer Money and Immutable History | **PASS, with a foundation obligation** | No money columns exist yet. The obligation is that the migration tool can emit raw `CREATE TRIGGER ... RAISE(ABORT)` DDL, since the principle demands database-level enforcement. drizzle-kit emits plain SQL migration files, so custom DDL can be added. Carried into research as a verification item. |
| V. Two-Phase Keyset Reads | **PASS, not exercised** | No paginated listing and no ordering columns exist in 001. |
| VI. Integration-Proven Verification | **PASS, directly exercised** | This is the substance of User Story 3. FR-016 through FR-021 encode real-database testing, per-test isolation, `DELETE FROM` cleanup, and non-zero exit on an empty run. Serial execution was clarified specifically so single-writer lock contention cannot masquerade as a defect. |
| Scope: NestJS, SQLite, Drizzle, single process | **PASS** | FR-013 and FR-014 encode the pragma and single-access-path rules directly. |
| Scope: single currency | **PASS, not exercised** | No money path in 001. |
| Quality gate: zero tests fails the build | **PASS** | FR-019. |

**Result: gate passes, zero violations.** One item is unresolved rather than violated, and it
is a decision the constitution itself forces into the open.

### Post-design re-check, after Phase 0

Re-evaluated against research findings. **No change: still passing, still zero violations.**
Research introduced no structure touching Principles I, IV, or V, and it strengthened the
Principle II position by turning changed-row-count support from an assumption into an explicit
selection filter.

The second clarification round added FR-015's prohibition on applying migrations during
startup. Re-checked against Principle VI: it strengthens rather than threatens the gate,
because the test harness already applies migrations explicitly to its throwaway database
(FR-018) rather than relying on a boot-time side effect.

Research surfaced one thing the initial gate did not anticipate: `@libsql/client` is a
SQLite-compatible **fork**, not SQLite, while the constitution's Scope section names SQLite.
Selecting it would have been a governance question rather than a purely technical one.

**That question is now moot.** The selected driver reports SQLite 3.53.4, genuine SQLite, so
**no constitutional amendment is required**. The experiment also verified the two foundation
obligations directly rather than by inference: the driver reports a changed-row count, which
Principle II decides a 409 from, and it supports native transactions, which Principle III needs
for per-chunk commits. Both are now demonstrated rather than assumed, which is the strongest
form this gate has been in.

The first run of this command generated only `research.md`, on the grounds that the other
artifacts would have been filler. That is no longer true. The clarification round pinned the
configuration defaults, which gives `data-model.md` real content, and it settled the health
check's success and failure semantics, which gives `contracts/` something to specify.

### Source Code (repository root)

```text
src/
├── main.ts                    # Bootstrap and shutdown hooks (FR-032 to FR-034)
├── app.module.ts
├── config/                    # Schema-validated env loading, fail fast (FR-005 to FR-009)
├── database/
│   ├── schema/                # Drizzle schema modules, single source of truth (FR-010)
│   ├── client.ts              # Connection and startup pragmas (FR-013)
│   ├── migrate.ts             # Migration application entry point (FR-011)
│   └── migration-state.ts     # Startup check, refuse to boot if pending (FR-015)
├── health/                    # Unversioned health route (FR-030, FR-035)
├── logging/                   # Structured logger and redaction (FR-031)
└── scheduler/                 # Placeholder recurring task, overlap guard (FR-026 to FR-029)

test/
├── setup/                     # Throwaway DB lifecycle, per-test DELETE FROM (FR-017, FR-018)
└── integration/               # Real-database integration tests (FR-016)

drizzle/                       # Generated, committed migration files (FR-012)
drizzle.config.ts
.env.example                   # Every recognised setting, no secrets (FR-008)
```

**Structure Decision**: A single project using the NestJS convention of `src/` beside a
top-level `test/`, organised by feature module rather than by layer. Each directory above maps
to exactly one user story in the spec, which keeps task decomposition and the constitution's
review checklist aligned with the folder they apply to. There is no `models/` directory,
because 001 has no domain entities and creating an empty one would invite someone to fill it.

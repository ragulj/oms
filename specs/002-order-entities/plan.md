# Implementation Plan: Order Entities

**Branch**: `002-order-entities` | **Date**: 2026-09-05 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/002-order-entities/spec.md`

## Summary

Add the persistent data model for orders and order line items, plus the two minimal placeholder
tables their foreign keys point at. The model carries no behaviour: it is a set of guarantees that
the database itself holds, so that every later specification inherits them rather than re-asserting
them.

The technical approach is settled by what the toolchain can and cannot express, which Phase 0
verified empirically rather than assumed. Column-level guarantees (closed status set, integer type
enforcement, monetary bounds, quantity floor, line total arithmetic) go in the Drizzle schema as
`check()` constraints and one stored generated column, and `drizzle-kit` emits all of them
correctly. Row-level guarantees (immutability of line items against update and delete, a frozen
creation timestamp, an automatically maintained last-changed timestamp) are triggers, which Drizzle
has no way to express, so they ship in a `drizzle-kit generate --custom` migration that is still
generated by the tool, still registered in the journal, and still applied by the standard migrator.

## Technical Context

**Language/Version**: TypeScript 5.9.3 targeting Node.js 22 or newer, as declared in
`package.json` engines. Development and verification here ran on Node 24.19.0. Module format is
unchanged from Spec 001: CommonJS output against ESM-only NestJS packages, which coexist through
Node's `require(esm)`.

**Primary Dependencies**: `drizzle-orm` 0.45.2 and `drizzle-kit` 0.31.10 for schema definition and
migration generation, `better-sqlite3` 13.0.3 as the driver. That driver bundles SQLite 3.53.4,
verified by querying `sqlite_version()`, which is comfortably above the 3.31 floor that stored
generated columns require.

**Storage**: A single SQLite file, opened with `journal_mode = WAL`, `foreign_keys = ON`, and
`busy_timeout = 5000`, per the connection settings Spec 001 already applies.

**Testing**: Jest 30 with ts-jest, `maxWorkers: 1`, launched as
`node --experimental-vm-modules node_modules/jest/bin/jest.js`. Every test runs against a real
database file.

**Target Platform**: A single Node process against a single database file, per the constitution's
scope constraints. Local development and automated test execution only.

**Project Type**: Web service. This feature contributes only its persistence layer.

**Performance Goals**: The three committed access patterns in FR-036 through FR-038 must each be
served by an index rather than a full table scan, verified against at least 10,000 orders per
SC-007. No latency target is set. Spec 001's advisory two-minute budget for full verification still
applies, and the table rebuild introduced by FR-025c is the change most likely to erode it.

**Constraints**: Single writer, so no concurrency beyond what the conditional update in Principle II
settles. Monetary values are integers in the range 0 through 9,007,199,254,740,991. Timestamps are
integer microseconds since the Unix epoch. No currency column anywhere. Triggers cannot be expressed
in a Drizzle schema module, which is the one place this plan departs from the constitution's
single-source-of-truth rule and is recorded in Complexity Tracking below.

**Scale/Scope**: Four tables, two of them deliberately throwaway placeholders. Roughly 10,000 orders
in the largest test fixture. The specification's Assumptions record that no real production volume is
established, and that this figure is a fixture size rather than a capacity claim.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

Evaluated against constitution **v2.1.0**. That version is itself an input to this plan: it was
amended during clarification of this feature, so Principle IV now covers deletion and Principle VI
now states isolation as a property rather than as the `DELETE FROM` mechanism alone.

| Principle | Verdict | Basis |
| :--- | :--- | :--- |
| I. Centralized State Machine | **PASS** | This feature adds no transition logic. FR-030 forbids the status field from encoding any transition rule, ordering, or precedence, which keeps the future state machine the only authority |
| II. Lock-Free Atomic Transitions | **PASS** | FR-029 requires the column to support the conditional update, and Phase 0 verified the changed-row count is 1 on match and 0 on miss. FR-034b additionally requires that timestamp maintenance not inflate that count, which Phase 0 also verified |
| III. Bounded Background Processing | **PASS** | The job itself is a later feature. This plan supplies what it needs: FR-037 requires the bounded claim to be index-served, which is the property that stops a chunk from holding the write lock for the length of a scan |
| IV. Exact-Integer Money and Immutable History | **PASS** | Money is `INTEGER` with a `typeof` guard and explicit bounds (FR-011 to FR-019). Captured price and description are frozen. Under v2.1.0 the immutability triggers cover `DELETE` as well as `UPDATE`, which FR-025a requires |
| V. Two-Phase Keyset Reads | **PASS** | FR-031 mandates integer microseconds and bans text and real representations. FR-036 and FR-038 require an index for the keyset page and the line-item fetch, which is the two-phase shape |
| VI. Integration-Proven Verification | **PASS** | FR-042 requires every constraint, trigger, and index to have a test exercising the failure mode it prevents. FR-025c uses the rebuild that v2.1.0 names for tables refusing deletion, and FR-025d keeps `DELETE FROM` mandatory where it still works |
| Scope: single currency | **PASS** | FR-020 forbids a currency code column or any multi-currency structure |
| Scope: Drizzle as sole persistence path | **PARTIAL** | Migrations are generated by drizzle-kit and committed, and all SQL runs through Drizzle's migrator. But trigger DDL cannot live in a Drizzle schema module, so those modules are not the complete source of truth. Recorded in Complexity Tracking |
| Workflow: build fails on zero tests | **PASS** | `passWithNoTests: false` is unchanged from Spec 001 |

**Gate result: PASS with one recorded deviation.** No unjustified violation. The single deviation is
forced by the toolchain rather than chosen, and is documented below with the alternatives that were
rejected.

Re-evaluated after Phase 1 design: unchanged. The data model introduced no new deviation, and the
contract in `contracts/persistence.md` states the guarantees in the same terms the principles use.

```text
│   ├── orders.ts             # orders table, checks, indexes
│   └── order-line-items.ts   # line items, checks, generated column, index
├── client.ts                 # unchanged from Spec 001
├── migrate.ts                # unchanged from Spec 001

drizzle/
├── 0000_certain_silverclaw.sql   # Spec 001, unchanged
├── 0001_<generated>.sql          # tables, constraints, generated column, indexes
├── 0002_<custom>.sql             # triggers, written by hand into a drizzle-kit --custom file
└── meta/_journal.json            # extended by drizzle-kit, both entries registered

test/
├── setup/
│   ├── per-test.ts           # DELETE FROM, now restricted to tables that permit it
│   ├── rebuild.ts            # new: drop and recreate the tables that refuse deletion
│   └── database.ts           # unchanged
└── integration/
    └── orders/               # constraint, trigger, index, and round-trip tests
```

**Structure Decision**: The schema module is split into one file per table rather than kept as the
single `index.ts` Spec 001 created. Four tables with constraint blocks, a generated column, and index
definitions would make one file long enough that the constraints stop being reviewable, and the
review checklist in the constitution asks a reviewer to check exactly those constraints. `index.ts`
remains the barrel and keeps owning `ALL_TABLE_NAMES`, which the test harness reads.

## Complexity Tracking

> **Fill ONLY if Constitution Check has violations that must be justified**

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Trigger DDL lives in a hand-written migration rather than in a Drizzle schema module, so those modules are not the complete source of truth for the schema | Constitution Principle IV mandates that immutability be enforced by a SQLite trigger calling `RAISE(ABORT, ...)`, and forbids relying on an application-layer guard. Drizzle 0.45.2 exposes no trigger construct, verified by inspecting every export of `drizzle-orm/sqlite-core`. Principle IV and the single-source-of-truth rule cannot both be fully satisfied with this toolchain, and Principle IV is the one that protects financial history | Enforcing immutability in application code was rejected outright: Principle IV names that failure mode explicitly, and an application rule is one forgotten code path away from failing. Waiting for Drizzle to add trigger support was rejected as unbounded. The chosen form keeps as much of the rule as remains available: the migration is still generated by `drizzle-kit --custom`, still registered in `meta/_journal.json`, still committed, and still applied by the standard migrator, so there is no second migration path and no ad hoc execution outside Drizzle |
